# 游戏运行时重构实施步骤

状态：实施计划，尚未执行；不是进度记录，也不表示新协议已可用。
前置文档：[目标设计](./game_runtime_design.md)、[构建与测试](../engineering/build_and_test.md)。

## 执行约束

- 每一步均交付可运行代码、对应测试及必要契约更新，不以“下一步会补齐”作为本步通过依据。
- 独立验收指在列明的前置步骤完成后，能单独运行本步测试；不意味着步骤彼此无依赖。
- 每一步可形成独立提交；旧卡保持可运行，新模式在完整交付前仅供测试/开发验证。
- 新模式入口默认不向普通玩家开放；平台不得接受新清单后回落到旧执行器或静默忽略字段。
- 不复制规则引擎、模型传输或双端存储体系，不为通过重构删除旧卡回归或降低覆盖率门槛。
- Schema、契约测试、运行实现同步修改；每个仓库文件不超过 200 行，按现有规则拆分。
- 新增测试接入现有测试发现与 CI；不堆叠只验证文件名、源码片段或偶然布局的测试。

## 测试基础与验收方式

单元测试验证状态和执行语义；集成测试验证真实模块组合、文件与持久化边界；E2E 只验证宿主、交互与完整流程。
准备独立最小 fixture，不依赖 WA2：旧卡、仅 JS 新卡、Judge + Narrator 新卡、恶意/损坏卡。
模型使用可控制请求完成顺序的假传输，端到端使用本地 SSE 服务，不依赖真实密钥或模型随机行为。
异步测试使用显式屏障/可控时钟，不通过增加固定等待时间掩盖竞态。

每步提交前执行 `npm run lint`、`git diff --check` 和本步相关测试；文档-only 决策内容不单独冒充实现验收。
JS 全量回归使用 `npm run test:js`；文件/schema 集成使用 `npm run test:integration`；涉及 Rust 使用 `npm run test:rust`。
桌面/Web 构建分别用 `npm run renderer:build`、`npm run web:build`；真实宿主用 `npm run test:tauri` 和 `npm run test:web:browser`。
定向测试路径在对应代码落地时记录到构建文档；不在本计划预先宣称不存在的测试命令可用。

## 步骤 1：提取无界面的生成内核，锁定旧卡行为

依赖：无。

- 交付：从聊天 UI 中抽出模型调用、响应解析和规则执行的可注入内核；现有聊天作为调用方接回。
- 范围：不增加多 Agent，不改变旧卡流式 patch、阅读提交、取消及重试行为；梳理依赖，避免内核引用 React/DOM。
- 测试：对既有正常生成、分段阅读、校验重试、网络失败、主动取消建立行为回归；以 memory adapter 在无界面环境跑完一次生成。
- 验收：内核不挂载聊天组件也能运行；旧卡与普通聊天回归通过，桌面和 Web 均能构建并完成既有游玩冒烟。

## 步骤 2：落实新清单与 Agent 定义的加载契约

依赖：步骤 1。

- 交付：定稿协议标识、主程序/UI 入口、Agent 文件、模型引用及内容授权字段；在唯一共享 schema 中提供明确版本分支。
- 范围：实现新卡内存/文件加载器，区分“结构有效”和“平台允许运行”；普通导入暂不开放新模式。
- 测试：有效新卡/旧卡、未知版本、缺失入口、无效 Agent、非法路径、越界引用，以及 JS/Rust schema 一致性。
- 验收：最小新卡被解析为明确的运行定义；错误定位到文件和字段，非法输入在执行前失败；旧卡加载结果不变。

## 步骤 3：建立可提交、可校验的共享 State Store

依赖：步骤 2。

- 交付：复用现有 State schema/default/patch 能力，加入快照、变更集合、版本、订阅和统一提交接口。
- 范围：明确 JS 与各 Agent 的写入权限；规则/exec 在受控草稿中计算，禁止绕过提交入口修改共享对象。
- 测试：默认值、合法修改、非法/越权修改、失败不部分提交、外部引用不可偷改、订阅顺序和祖先/子路径写冲突。
- 验收：合法提交只产生一次可追踪变更；过期或冲突提交被拒绝，不覆盖其他修改；旧模式状态语义仍由兼容路径保持。

## 步骤 4：实现独立 Agent Runtime 与顺序协作

依赖：步骤 1–3。

- 交付：每 Agent 独立 Messages、初始化标记、规则上下文和模型引用；复用生成内核执行一次完整调用。
- 范围：新模式暂存调用中的 Messages/变量变化，接受响应并完成后处理后统一提交；无 UI 自动演出副作用。
- 测试：上下文/TTL/初始化隔离、Judge 写变量后 Narrator 模板读取、非法 patch、校验重试、后处理失败和调用失败。
- 验收：无界面 fixture 完成 Judge → Narrator → `text`；等待调用返回时结果已提交，失败不留下半次调用的 Messages/State。

## 步骤 5：实现受控主程序与纯 JS 游戏循环

依赖：步骤 4。

- 交付：明确启动、恢复、玩家事件、停止入口；实现卡内模块加载和受控 State/Agent API，独立于现有短时 exec。
- 范围：普通玩家行为默认顺序分发；卡片可用 JS 做结算和分支。模型等待不占用短脚本超时，但失控计算必须可终止。
- 测试：真实执行宿主加载本地模块、纯 JS 推进、JS/Agent 混合流程、事件顺序、异常、模块越界及死循环终止。
- 验收：无需聊天组件，主程序即可消费玩家事件并更新状态；错误包含脚本位置，停止后不能继续写入，无法访问宿主或密钥。

## 步骤 6：增加并行、后台任务与生命周期隔离

依赖：步骤 5。

- 交付：等待调用、并行调用和显式后台任务句柄；同 Agent 队列、任务状态、取消、超时、调用预算及运行代次。
- 范围：不同 Agent 可并行；写冲突拒绝提交，主程序处理失败；提供业务前置条件校验，不做自动依赖图。
- 测试：用屏障排列先后完成顺序，覆盖同 Agent 排队、独立路径合并、同路径冲突、过期业务结果、取消与超时。
- 验收：后台任务可跨一次事件处理继续运行，但不可跨已停止的 Session 写回；未等待任务的异常可观察，任务结束后无残留句柄。

## 步骤 7：交付卡内前端宿主与资源桥

依赖：步骤 2、5、6。

- 交付：用双端可运行原型确定隔离容器、消息桥和模块/资源加载方式，随实现固化安全契约；加载卡内 UI 入口。
- 范围：前端发送玩家事件、读取/订阅获准状态，主程序发送展示事件；不获得任意 native API、平台 DOM 或模型密钥。
- 测试：真实 WebView/浏览器内验证桥消息身份、非法载荷、跨卡/路径越界、HTML 注入、资源 MIME、子路径部署和卸载清理。
- 验收：仅 JS fixture 在桌面/Web 显示独立 UI 并响应操作；攻击 fixture 不能越权，切卡后监听器、媒体和资源句柄被释放。

## 步骤 8：打通变量到卡内演出的最小闭环

依赖：步骤 4–7。

- 交付：最小游戏卡主程序调用 Judge/Narrator，Narrator 只更新 `text`，卡内模块固定正文副本并逐段显示。
- 范围：使用简单卡内背景/音频展示资源控制权；不引入平台级演出 DSL，不预设 `text`/`scene` 的自动行为。
- 测试：单元测试分段和推进；E2E 验证玩家输入、真实 SSE、规则注入、变量提交、显示及资源解码/播放。
- 验收：仅更新 `text` 不自动展示；主程序触发展示后可逐段推进；后台改写 `text` 不改变已开始播放的正文。

## 步骤 9：完整 Session、检查点与恢复

依赖：步骤 6、8。

- 交付：带版本的完整快照，包含 State、所有 Agent 历史及初始化标记；提供检查点和卡内恢复入口，不序列化 JS 调用栈。
- 范围：约定一致快照边界，保存已提交状态和未完成业务阶段；恢复后不自动重放模型调用，由主程序明确重发或放弃。
- 测试：存档读写往返、保存中调用提交、写入失败保留旧档、损坏存档拒绝覆盖、重启恢复、回滚后迟到任务失效。
- 验收：正文播放中保存并重启，内容和段落位置一致，全部 Agent 历史恢复且 init 不重复；回滚不会残留后续演出或变量。
- 双端要求：桌面自动保存与 Web 显式新建存档均验证；未完成 Promise 不恢复，不增加存档转移功能。

## 步骤 10：接通导入、发布、静态检查与运行日志

依赖：步骤 2–9。

- 交付：新卡接入桌面导入和 Web 静态发布/缓存；dry-run 校验入口、模块、Agent 引用、schema 与规则。
- 范围：trace 记录 agentId/callId、调用生命周期、变量提交/冲突和脚本来源；复用现有开发者模式，不增加 Web 开发者模式。
- 测试：导入→运行、发布→下载→运行、缺资源/损坏哈希、越界引用、dry-run 不发模型请求、错误来源及日志敏感信息排除。
- 验收：同一新卡可经正式资源管线进入双端；Agent 可凭静态检查定位错误文件，凭桌面 trace 还原多 Agent 失败链；密钥不进日志。

## 步骤 11：提取官方可选演出库，完成旧卡兼容

依赖：步骤 8–10。

- 交付：将可复用背景、立绘、BGM 和阅读交互整理成随卡分发的库；新卡显式引用，非平台隐式加载。
- 范围：旧卡通过兼容执行路径保留原行为；逐项迁移可共享部分，不强行把旧流式提交改成新模式批量提交。
- 测试：库行为单元测试；旧卡流式/阅读/重试/演出回归；旧存档加载不迁移破坏；示例卡与不依赖该库的卡都可运行。
- 验收：普通聊天、原生旧卡及酒馆转换卡无行为倒退；新卡能替换前端而不改变 Agent 数据接口，无需全局安装库。

## 步骤 12：完整双端验收并开放新模式

依赖：步骤 1–11 全部通过。

- 交付：更新当前协议文档、开发参考、初始化模板和离线 devkit，开放新模式；目标草案不再被误当作唯一使用说明。
- 测试：运行现有 JS/集成/Rust 套件和新增用例；Chrome/Firefox/Safari 与 Windows/macOS/Linux Tauri E2E 全部通过。
- 端到端主线：安装/下载 → 启动 → 玩家操作 → 多 Agent 变量协作 → 分步演出 → 保存 → 重启恢复 → 切卡/卸载。
- 故障主线：模型失败、非法 patch、并发冲突、后台取消、资源缺失、保存失败；结果可诊断且不污染其他 Session。
- 验收：生产构建不含测试绕过入口；旧卡回归、资源隔离、显式/自动保存均通过；按现有 CI 策略验证构建，不额外重复打安装包。

## 暂不纳入首轮

跨应用关闭恢复请求、任意 JS 栈快照、自动任务依赖图、通用演出 DSL、全局包管理、3D 引擎实现及存档转移。
逐 token 写入并演出可后续设计；首轮以完整调用接受后提交变量为新模式验收基准，不改旧卡流式能力。
