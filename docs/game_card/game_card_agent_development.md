# Agent 辅助游戏卡开发设计

状态：[离线开发包](./game_card_devkit.md)、[项目初始化与 GUI 起步指令](./game_card_project_init.md)、[客户端 dry-run](./game_card_dry_run.md) 和 [开发者模式运行日志](./game_card_runtime_trace.md) 已实现。日志具体字段、完整性与静态/运行边界见对应文档。

## 目标与范围

开发者在自己使用的 agent 工具中创建目录、描述需求，由 agent 初始化和编写游戏卡，调用客户端 dry-run 检查语法。开发者在平台中开启开发者模式并实际游玩后，agent 再通过 session 中的运行日志定位消息或变量行为与预期不一致的原因。

- 开发包随客户端安装，初始化不依赖网络下载、平台源码或额外 npm 包。
- 开发指南和 DSL spec 使用普通 Markdown 文档，不生成 `SKILL.md` 或专用 skill 目录，不依赖 agent 工具的安装、发现或激活机制。
- 客户端直接提供统一调用入口，不向游戏卡仓库分发 Shell、PowerShell 或 Node 启动脚本，也不要求额外解释器。
- 不引入 MCP、独立 CLI 安装包、开发工具断言语法或测试框架。
- dry-run 只做语法及静态引用校验，复用平台校验能力；不执行游戏卡规则、不创建 session、不生成 trace log。
- 实际运行与行为排查发生在平台正常游玩流程中，不设计模拟游玩或无头执行链路，不新增专门的调试窗口。
- trace 就是开发者模式下实际游玩产生的运行时 log，保存在对应 session 中，重点忠实记录游戏卡规则对 `messages` 和 `state` 的影响，不建设独立回放系统或查询服务。

第一版支持能够访问项目目录并启动本机客户端的 agent 环境，不承诺远程服务器、容器或无桌面环境直接可用。游戏卡仍使用现有协议，不增加 agent 专属卡类型。

## 离线分发与起步引导

客户端资源中携带版本化开发包：Markdown 开发指南、DSL spec 参考文档、内置 lib 索引、最小游戏卡模板、可选 lib 及配套文档。资料注明对应版本，发布时从同源代码与文档生成，不维护另一套 Schema 或库实现。

- `.wcs/development.md` 是普通 Markdown 开发指南，描述项目目录约定、组织规则或 exec、选用 lib、调用平台、阅读日志和修改卡片的工作流程，并提供相关文档入口。
- DSL spec 是供 agent 理解和按需查阅 DSL 语法、语义的参考文档，说明字段、参数、默认值、规则阶段、action、predicate、模板、exec 和资源引用，并提供示例。它不是校验器或运行配置，不承担自动检查职责。
- `.wcs/libs.md` 是内置 lib 的简短索引，列出用途、适用场景、版本、主要限制，以及获取库和详细文档的方式，帮助 agent 选型；它只做导航，不重复维护各库详细说明，也不是运行时注册表。
- 每个 lib 的 README、运行语义等详细文档跟随该库的脚本分发；平台不赋予 lib 不同于普通 exec 的加载或权限语义。
- 开发资料必须自包含、相对链接有效，不依赖开发者访问平台仓库里的源码路径。

DSL spec 从现有 DSL 文档整理，与对应平台版本的协议和运行语义保持一致；不要求把 JSON Schema 副本作为项目的执行依赖。结构校验仍由客户端使用平台唯一 Schema 完成，见 [协议 Schema](./game_card_schema.md)。平台不读取项目内 spec 文档来执行游戏卡，修改文档不会改变运行行为。

系统配置的“游戏卡开发”区域提供“复制给 agent 的开发指令”，只给出文档阅读指引，以及 JSON 格式的本机客户端、游戏卡数据目录 `gameCardsPath`、开发指南、DSL spec 和 lib 索引路径。具体操作统一查阅开发指南，不重复初始化命令或开发流程，不要求修改全局 PATH 或猜测安装目录。按钮只复制文本，不选择目录或创建项目；剪贴板不可用时展示可手动复制的完整文本。

用户首次获取后可将这段指令重复用于不同项目，无需每次回到 GUI 选择目录。客户端移动或重新安装后重新复制；AppImage 内置资料位于临时挂载目录，阅读期间保持客户端打开。以后可保留 GUI 初始化作为辅助入口，但必须复用同一初始化实现。

普通文档不保证被 agent 自动加载。起步指令要求先阅读 `guidePath` 对应的客户端内置开发指南；初始化结果再要求阅读项目中的 `.wcs/development.md`。新会话同样需要阅读入口指引，再按需查阅 spec、lib 索引和库文档；不修改或覆盖已有 agent 配置。

lib 默认由 agent 根据游戏卡需求选择，开发者显式指定或限制时以开发者要求为准。普通选型无需逐项确认，存在明显功能取舍时再询问；不默认复制全部库，也不自动联网获取未知库或覆盖已接入的库。

## 开发工作流

1. 开发者安装客户端，在 agent 工具中创建或打开目标目录。
2. agent 查阅客户端内置开发指南和 lib 索引，根据需求选型，再调用客户端初始化项目；开发者不必预先指定库名。
3. 客户端复制离线资料，生成卡骨架，报告生成结果和指南位置。
4. agent 阅读项目内指南，编写规则、状态、脚本和内容资源。
5. agent 调用客户端 dry-run，读取校验结果，修复语法或静态引用错误后再次检查。
6. 开发者将卡加载到平台，在标题栏开启开发者模式并实际游玩，在对应 session 中自动生成 trace log。
7. 行为与预期不一致时，开发者直接让 agent 排查当前会话；agent 通过既有 active/index 文件定位日志，根据实际消息、状态变化定位问题；修改后重新检查语法，再由开发者加载更新后的卡验证行为。

语法正确不代表行为符合预期。dry-run 不负责复现剧情或判断行为；不要求开发者准备模拟输入、编写断言，也不自动把运行日志转换为回放包。

## 项目内容与所有权

以下布局为建议，`card.json` 仍位于卡根目录：

```text
card.json
rules/
state/
lib/worldbook/                         # 按需复制的脚本和配套文档
worldbook/config.json                  # 卡自己的配置
worldbook/entries/                     # 卡自己的正文
.wcs/
  development.md                      # 普通 Markdown 开发指南和阅读入口
  libs.md                             # 内置 lib 简短索引，用于选型
  spec/                               # DSL 语法、语义及示例参考文档
```

第一版不生成 `devkit.json`、`inputs/`、`local.json` 或 `runs/`。版本说明放在开发指南和库文档中，客户端位置由本机起步指令提供；dry-run 无需运行输入，trace 属于平台中的实际 session，不属于开发资料目录。

客户端内置开发包是只读原件；项目里的资料和 lib 是固定版本的独立副本，可以随 Git 提交。不能通过软链接引用客户端内部资源，也不能在运行时在线下载 lib。

初始化复制完整 lib 索引，但只复制选定库的脚本和配套文档；索引列出某个库不代表该库已接入。未选用库的详细文档可以从本机开发包离线查阅，选用后以项目内对应版本的文档为准。客户端资源位置由本地起步指令提供，不把机器绝对路径写入可提交的索引。

[世界书 lib](../../libs/worldbook-library/README.md) 的配置和正文仍属于卡内容，entry 不逐个注册到 `card.json`；继续通过目录 scope 授权。初始化选用世界书时生成对应配置、目录授权和 exec 接入，不发明新的世界书语法。

Git clone、目录移动或重新打开项目不需要平台内部的“已初始化项目”记录；本机客户端位置失效时允许重新定位，不重建卡内容。

## 客户端初始化与调用

客户端提供跨平台一致的参数与结果语义；可执行文件位置因系统而异。以下 `client` 仅代表实际客户端路径；`--init-project` 和 `--dry-run` 均已实现：

```text
client --init-project . --lib worldbook
client --dry-run .
```

初始化只读取内置开发包并写入指定目录，不需要进入游戏运行环境。新项目生成唯一卡 ID 和最小有效骨架；已有项目仅补充缺失的开发支持。重复初始化不改变已有 ID、规则、配置、正文或 lib。

写入前检查路径和文件冲突，禁止越过目标目录或通过链接写到目录外。默认不覆盖已有文件；失败只清理本次创建且未被用户改动的内容，不能替换整个已有仓库。初始化不隐式执行 Git 初始化、提交、远程发布或模型配置修改。

初始化与资料更新分开：更新必须显式发起并识别本地修改，不将“再次初始化”当作覆盖升级。

命令必须提供 agent 可观察的完成边界、机器可读结果及退出状态。初始化报告文件处理结果；dry-run 报告检查范围和校验诊断，不返回 session 或 trace 路径。校验错误或检查无法完成返回非成功状态；警告单独列出。校验通过不代表运行行为正确。

## dry-run：语法与静态校验

dry-run 读取指定项目，复用平台的卡加载、`$import`、唯一 Schema 和静态检查能力；不把校验器复制到开发包，也不要求 agent 使用独立 Node 脚本检查。

检查范围：

- JSON 解析、游戏卡结构、规则、action、predicate 及参数是否符合平台协议。
- `$import` 与静态 include 的路径安全、文件存在、循环引用等加载约束。
- 已声明资源、目录 scope 和可静态确定的引用是否合法，外部 state schema 是否有效。
- 平台支持静态解析的模板、表达式、正则和 exec JavaScript 语法；复用正式解析或编译逻辑，但不求值、不执行脚本顶层代码或调用 `run(ctx)`。

动态构造的路径、变量值、lib 内部业务约束和分支结果不属于静态校验能够保证的范围。结果应说明未覆盖的检查，不能为了验证这些内容而执行规则或脚本。

dry-run 不触发 `init` 或其他规则阶段，不需要初始 messages/state、用户输入、模拟模型响应或阅读事件；不发起模型请求，不生成运行日志，也不判断剧情是否符合预期。

检查只读项目内容，不执行普通导入的安装或激活步骤，不创建临时或正式 session，不切换 active card，不修改卡片、玩家存档、模型配置或已有会话。

客户端自动完成检查并返回结果，agent 不需要点击窗口。调用不能关闭用户原来运行的客户端；无需为语法检查构建无头游戏运行环境。

校验诊断包含稳定错误类别、原因和源文件位置，可用时提供 JSON Pointer 或行列号。该命令结果是语法检查报告，不是 trace log，也不保存到 session。

## 开发者模式：实际游玩与日志归属

开发者在平台中开启开发者模式后，通过正常游玩操作复现行为问题。平台沿用 [游戏卡运行流程](../game_card_design.md)，包括真实输入、模型响应、阅读推进、重试和保存；开发者模式只增加诊断记录，不替换模型、不改变规则阶段、超时或状态提交语义。

只有开启开发者模式的实际游玩过程生成 trace log；未开启时不写入该日志，dry-run 也不写入。卡内脚本继续遵守资源 scope，不因开发者模式获得额外文件、网络或系统权限。

trace 跟随 [游戏卡 session](../chat_session_design.md) 保存，位置为：

```text
game-cards/cards/<card-id>/sessions/<session-id>/
  messages.json
  retry-base.json
  trace.jsonl                         # 开发者模式实际游玩时追加
```

这是平台数据目录中已加载游戏卡的 session，不是开发者源码仓库中的 `.wcs/`。日志写入绑定产生事件的卡和 session，切换会话后不能将旧会话尚未落盘的记录写到新会话。

标题栏将图标与名称拆成独立按钮：点击卡片图标切换开发者模式，点击名称打开切卡菜单；图标高亮与悬停提示表示记录状态，失败时明确提示。不额外放置文字开关，不在系统配置侧栏放置开关，不展示或复制日志路径。agent 从起步指令的 gameCardsPath 出发，通过卡和 session 的两级 active.json 定位当前日志，通过 sessions/index.json 确认名称；用户不需要知道 ID。切换后的旧会话按原名称、时间与预览确认。详见 [日志定位约定](./game_card_runtime_trace.md)。

不另建日志目录或查询服务。中途开启模式只记录后续过程，以当时 messages/state 为起点；不补造此前的 trace。关闭模式后停止记录，已有日志保留。

## 运行日志：规则对 messages 和 state 的影响

### 记录内容

日志帮助回答“为什么没有生效”“被谁改掉了”，不只记录异常。以下记录均指开发者模式下实际游玩的 session trace，与 dry-run 校验诊断分开。

建议在 session 的 `trace.jsonl` 中按顺序追加，区分每次启用记录及各轮执行。开始或恢复记录时保存平台版本、卡内容指纹和当前 messages/state；各轮记录实际执行阶段、结果、错误和警告，未完成的执行明确标记，不引入单独的 trace 服务或回放协议。

规则和 action 节点至少记录阶段、顺序、规则 ID（若有）、嵌套 action 位置、源文件位置及执行状态：

- 条件是否命中、是否跳过，以及相关实际判断值；短路未求值项明确标记，不重复计算条件来生成日志。
- 消息插入、删除、修改和重排，包含实际位置及完整旧值、新值，保留正文、role、TTL 和 `_meta`，不按 UI 可见性过滤。
- 状态创建、修改、删除，记录具体路径和旧值、新值；必要时区分尝试写入、schema clamp 后结果与最终提交。
- `find` 临时状态的建立、遮蔽与恢复，不能让局部变化看起来已持久化。
- exec 的输入输出变化、资源读取、耗时、effects 和失败；无法可靠对应返回消息时记录整个数组替换，不猜测来源。
- TTL 衰减、过期删除、state patch 处理和回滚等平台步骤，避免将这些影响误归因给某条规则。

不能只记录消息数量或 changedKeys。可从初始值及精确变化理解任意节点的实际 messages/state；为控制重复内容，可以记录精确差量，但不能静默省略影响判断的正文或状态值。

日志是诊断输出，不是第二份参与游戏逻辑的历史。无变化、未提交和已回滚必须可区分；执行过程中逐步记录，失败前的日志不能因最后一个 action 抛错或 Worker 超时而丢失。

### 原文件定位与 lib 诊断

保留 `$import` 展开及 JS include 拼接的位置映射，日志定位到原文件、JSON Pointer 或脚本位置；可用时补充行列号，不能只有展开后的 `rule[n]`。错误保留稳定类别和原始原因。

平台能记录 exec 整体输入输出，不能凭结果推断 JS 所有局部变量。lib 可通过现有 effects 等诊断输出解释内部选择；世界书可报告选中、预算排除和警告，同时由消息日志显示真正的注入、修改或后续删除。

第一版不新增通用逐行 JS 调试器或专用 lib 日志协议；先保证规则、action 边界和既有诊断不丢失。

## 版本、隐私与玩家分发

- 开发指南标明开发包与协议版本，库文档标明 lib 版本，不为此新增必需的 `devkit.json`；卡顶层 `version` 仍是卡内容版本，不变成协议选择器。
- 客户端升级只更新内置开发包，不自动修改已有项目；校验结果和运行日志报告实际平台版本，明确不兼容时拒绝，不静默下载或切换版本。
- 卡资源、lib 及配套文档进入玩家包；`.wcs/` 中的开发指南、spec 和 lib 索引默认不进入玩家包。
- 本机路径、session 和完整日志不提交 Git，也不进入玩家包；不得仅依靠 `.gitignore`，目录导入与导出必须明确排除开发资料和会话数据。
- 日志不包含模型密钥、认证头或无关用户配置。正文与 state 可能包含隐私，默认保存在本机，分享时显式选择内容。
- 日志超过容量或写入失败时必须报告不完整，不能将截断后的记录称为完整日志。
- 保持原有超时和状态语义，记录不应重复执行表达式或额外改变游戏逻辑；不承诺相同输入下随机分支、机器耗时或超时必然一致。

## 实施边界与验收

Schema、共享规则核心、Worker 和资源沙盒继续复用。离线开发包、初始化、GUI 起步指令、语法检查、实际运行位置映射和 session 日志已接通；运行日志保留规则/action 边界、原始 import/include 来源、msg/state 差量及失败前过程，不增加另一套运行时。

实施顺序：发布内置开发包与初始化能力，接通只读语法检查入口，再完善实际游玩中的开发者模式日志。检查复用平台校验器，日志接入现有运行链路；不增加模拟执行器或第二套运行时。

平台实现需验证：

- 断网、无 Node/npm、无平台源码时，agent 可以从空目录初始化并调用已安装客户端。
- 文件冲突、重复初始化和中途失败不覆盖原内容；目录复制后不依赖隐藏注册记录。
- dry-run 能定位无效语法和静态引用；不执行规则或 JS 顶层代码，不调用模型、不安装卡片、不创建 session 或 trace，不修改存档。
- 只有开发者模式实际游玩才写入对应 session 的日志；开关、恢复和切换会话不混淆记录归属，也不改变正常运行语义。
- 无断言也能通过日志看清规则对 messages/state 的具体影响，包括先插入后删除、临时状态恢复和错误前已执行过程。
- 校验错误与检查失败可被 agent 识别；实际游玩中的运行错误、超时和日志不完整如实记录，不能把语法通过当作行为验证成功。
- 初始化产物、版本更新、目录导入和打包遵守上述文件归属，lib 文档保留，开发日志与本机信息不泄漏。

验收目标：开发者只安装客户端，agent 在项目目录内离线完成初始化与语法检查；开发者在平台中开启开发者模式实际游玩，agent 读取对应 session 日志定位行为问题，修改后重新检查并交由开发者验证。不要求额外解释器、脚本矩阵、模拟输入或断言框架。
